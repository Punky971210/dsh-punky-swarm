> 蟛蜞模式治理引擎把公司的制度做成软件、装进引擎：排期、质检、审批、容灾逐条由引擎跑，不再靠人记住、靠人执行。制度装进去之后，人退到只剩裁决——不执行、不调度、不盯梢，说清要什么，验收做出什么。

## 一个人，一支队伍，和一条看不见的线

把 AI 当员工，是这两年流行的说法。员工要发工资、要管理、有情绪、会离职；手里的单个 Agent 没有这些毛病，随叫随到、按件计费、用完即走。它更像外包，不像员工——派活、盯活、验收，一个人管一个，管得过来。

但单个 Agent 的价值，到这里就到头了。

于是有人开始堆数量。十个 Agent 一起干活，比一个难管得多：谁先跑、谁等谁、谁写哪个文件、崩了从哪续，没有规则兜底，跑起来就是事故现场。堆出来的不是帮手，是更多要盯的外包。

真正的拐点不在数量，在治理。**外包靠人盯，部门靠制度。** 一个人盯不过来，一套制度可以。制度装进引擎之后，账也算得过来：部门要养编制，没活也得养；引擎里的制度按 token 租，有活才租。一个人、一套自动化的制度、一批随叫随到的 Agent——这就是一人公司的全部构成。

市面上的多 Agent 产品并不少，真跑成一人公司的却少见。多数产品卡在一条看不见的线上。这条线不画在愿景里，要拆开 Agent 才看得清它画在哪。

## 先拆开一个 Agent

就像互联网有通用的五层结构，一个 Agent 也能拆成四层：**底座、工具、能力、应用**。底座是 Agent 的操作系统；再往上是它能调用什么、能长成什么、最后交付什么。

对 Harness 来说，比的不是谁把底座挖得深，是谁把哪一层开给你。**开放的层级越多，能自定义的越多。**

开放程度大致分四档：

| 档 | 开的是哪一层 | 结果 |
|---|---|---|
| L0 能力层 | 模型、外部工具、技能可换可接 | 你能「用」引擎 |
| L1 流程层 | 引擎内定义任务流转，或在协议层外部编排多实例 | 你能在引擎外面加编排 |
| **L2 宿主层** | agent loop、会话日志、沙箱、界面皆可替换、可自托管 | 你能在引擎里「长」东西 |
| 纪律面 | 门禁、审批、存档、锁、审计 | **只有纪律有落座的位置，制度才装得进引擎** |

DSH 是本地进程插件树，全层级可替换：agent loop 本体就是插件，会话事件 append-only 全量留迹，模型可见即已记录，可搜索、可回放。**这套引擎跑在 DSH 上，不是选择口味，是纪律需要有地方落座。**

## 纪律在脊髓，不在脑

Agent 跑偏，靠更强的能力治不了，得靠纪律治。

拿走路说：走路这个技能刻在本能里，看上去再日常不过。真正要看的是，身体掌管走路的工具开放到了哪个程度——答案是脊髓。没了它，人就没法运动。而打字需要后天学习，依赖大脑、眼睛、手指，这些在演化史上比脊髓「年轻」得多。

**能力排在纪律后面。** 任务能不能按流程走完，不取决于它当下多聪明，取决于有没有一套流程在兜着它。传统 Agent Loop 每一步都在自我确认，前提是它相信自己知道对不对；可这个判断是当场生成的，这一刻的自信管不到下一步。引擎的做法是把判断权收走：开工前把契约立好，这一步交什么、什么算齐，写死在契约里；一步做完先验收，不过不放行，检查不落在 Agent 的自觉上，而拦在它调用外部工具的链路上。

把任务「脊髓化」，就是把三步一回头从流程里整个拿掉。这件事不在模型侧，在宿主侧——**宿主没把执行循环开到够得着的地方，纪律就没有落座的位置。**

## 三道坎，同一把钥匙

落地难，难在三处，而且都不在模型能力上。

| 坎 | 症状 | 引擎的对策 |
|---|---|---|
| **状态缺失** | 上下文一压缩、会话一关，做过的事就蒸发；中断一次等于从头再来 | **状态固化**：状态搬出模型脑子写进文件，文件是唯一事实源；每完成一个子步骤自动存一档，回来从最近一档续，做完的步骤不重做 |
| **目标漂移** | 聊着聊着需求就变了，没人察觉；每一步都自信，路上却没有人的判断锚点 | **判断力进门禁**：目标开工前钉死，批次建好中途绝不重算；想改目标就重新建批，那是明面上的决策 |
| **任务说不清** | 不知道让它干什么，于是只能说「帮我写个方案」 | **拆解做成例行工序**：先分级，再按依赖分层排轨，每轨声明自己交什么 |

一句话概括：**跑偏本身不可怕，人也会跑偏，可怕的是没人拦。**

## 它长在引擎里，不在协议外

第三方平台要把 Agent 连起来，靠 MCP、ACP 这类互联协议。它们解决的是「互通」：互相找得到、调得到工具、递得出任务。

问题在于，**互通之后最多组成聊天室与会议室，到此为止。** 真正的流水线不长在互通上，长在验收上——前脚没站稳后脚就不能迈，产物不齐绝不放行。这类检查只有一个位置能长：宿主执行循环内部。因为只有循环自己知道，这次调用前缺什么、这次产出了什么、谁在等这份产出。协议站在端点之间传话，传不动「这一步交齐了没有」。

做治理的也不止一家，但治理长在哪一层，答案不同：有的长在进程外与出口处，做成请求级拦截链；有的长在独立服务矩阵与会话层，管调度与消息；有的长在应用与协调层，由一个大模型充当 Leader。它们各有用途，但「让 Agent 记得做」和「引擎必须验」是两种治理。

**蟛蜞把制度放进执行循环**，所以它管的是「交没交、验没验、能不能收口」，而不是替 Agent 记住该交什么。

## 装进来你会得到什么

- **开工前先分级**：顺手的小活直接干，不背治理开销；环节多、要协作、要验收的活走整条流水线。**拿不准就判重**——判了重却不建批，引擎直接拒绝；评估会过期，防止一路闷头干下去。
- **批次按依赖分轨**：互不依赖的多轨并行，有依赖的排先后；启动之后不中途重排。轨内再分方案、执行、审查三层：方案没定稿执行不开工，执行没落盘审查不启动，审查不通过不算交付。
- **四道闸口**：派发前查上游产物齐不齐，合并前查计划结构全不全，结算前查产物落没落盘，收尾前查验收完没完成。缺一样就拒。
- **每完成一个子步骤存一档**：崩了不从头来；接手的执行者先查档，跳过已完成步骤。不自动续跑，恢复之前先看清档里是什么。
- **同一份活同一时刻只许一个写者**：多份活各用隔离工作区；冲突不自动合并、不静默覆盖，保留现场交人裁决。
- **全程留痕**：批次与成员状态、交接、结算、门禁判定全部落事件流，可回放、可导出审计。只读监控面板装在 Web UI 里，引擎只裁决不改写。
- **每次工具调用也能被裁决**：调用级护栏逐次判定，六种裁决原语覆盖放行、拒绝、转人工审批、收窄参数、延后与暂停；拒绝落可验篡改的收据，Agent 知道是哪条规则拦的。出厂规则为空，装上不改变既有行为。
- **随包 5 套团队技能**：软件工程、设计、调研、视频、写作。软件工程那套另含规格语言原文与适配层——写规格、查结构、验一致性都有据可依。

## 判据在开工前写死

把判断从 Agent 身上拿下来，装到一套它推不翻的手续里去——这条路近来也有人走。区别在**判什么**：

- 另一种做法是让另一个厂商的审查者判「做完了没有」，这是**终点判定**，裁量空间大，图的是两边裁量不相关。
- 蟛蜞的审计判的是**按计划里写下的验收标准逐条对不对**，这是**判据对照**，不做终点判定。判据在开工前就写死，落在计划层产物里；审计的取件必须锚定它，锚不上就拒派。想裁决，得先过判据门。

判据晚写一点，漂移就多一点。所以决定权交给代码：成员状态怎么迁移、批次什么时候能收口，由引擎状态机与相位机裁决，每一次迁移都进事件流——**Agent 只能提交，不能自己写结算。**

还有一件常被跳过的事：**停不下来。** 完成与否如果按「一轮」来判，这一轮装了多少文件、多少改动都没有上限，那「这轮完了没有」在提交那一刻本就模糊。蟛蜞的单位是**一步**：每走完一步存一档并带上步骤进度，判整件事有没有完，就退化成判最后一步走没走到。长跑探针也按状态分档给判据——执行中看总时长与无进展窗，待评审看待结算多久，空闲看待恢复多久，未派发看待派发多久；一把尺子量不了所有状态。停止是显式动作，不靠超时。

## 它管不到的地方

这一段比能力清单更重要。

引擎不判模型意图——护栏工作在工具调用层，模型自身的生成与推理不在防线内。不做沙箱，不做联网准入网关，不检测绕过显式通道的侧信道。不提供一次性写入存储，哈希链防的是静默篡改而不是删除，也没有第三方权威签名。判定不了调用者身份，留痕起记录与可见性作用，不构成访问控制。单机进程内治理，不做跨机编排。护栏出厂规则为空，裁决恒放行，配好规则才真正拦得住。

所以它不会替任何人宣称「防住了模型跑偏」。它提供的是一种位置选择：**把可判定的越界与交付缺失拦在执行期，而不是等它变成一份事后报告。**

## 谁该用

一个人，或者一个小型技术团队，做的是**有验收标准的交付**——代码、调研、设计、写作都算。

三个条件同时成立才值得：

1. 你同时在推进好几件事，不是改一个函数；
2. 你需要产物链可追溯、失败可查、越界能拦；
3. 你不愿意在 Agent 说做完了之后，自己再当一遍审查者。

三条同时成立的人不多。但如果你恰好是这种人，你会发现市面上没有第二个选择——这不是调研结论，这是当初自己动手写插件的原因。

不适合只想「一句话让 AI 把活干了」的场景。这套机制的开销全花在验收标准上，没有验收标准的活，用不上它。

## 安装

前置：已安装 DeepSeek Harness（dsh），Node.js ≥ 22。

```sh
# 安装并装入 dsh（profile 按实际使用的替换）
dsh plugin add dsh-punky-swarm
dsh web restart
```

> 备选：`npm install -g dsh-punky-swarm` 后以 `dsh plugin --profile <profile> add dsh-punky-swarm` 装入；开发路线可用 `link:` 指向本地包目录。

重启后会话区多出蟛蜞集群面板，团队技能自动同步到你的用户目录——**安装即得，无需额外配置**。

## 兼容性、读数与许可

**版本**以 `packages/dsh-punky-swarm/package.json` 为单一真源（变更记录见 `CHANGELOG.md`）。**测试基线**：**204 个测试文件 / 2,147 个测试 / 10,560 条断言 / 0 条恒真断言**（单一真源 `packages/dsh-punky-swarm/baselines/test-baseline.json`，本机 Node 24 实测，另在 Node 22 与 24 上持续校验）。

**peer 依赖**：`@deepseek-ai/dsh-tools`（^0.1.0-rc.6 || ^0.1.1-rc.2 || ^0.1.5-rc.1 || ^0.1.6-alpha.1 || ^0.1.7-rc.1 || ^0.2.0-rc.1 || ^0.2.1-rc.2）与 `@deepseek-ai/cordis`（^4.0.1）；零第三方运行时依赖。

**诚实边界**：面向单机进程内治理——不做分布式集群同步、无成本控制、无模型分层路由，零云依赖、默认零网络暴露；失败即终态，重做即新建批次，不自动续跑。
