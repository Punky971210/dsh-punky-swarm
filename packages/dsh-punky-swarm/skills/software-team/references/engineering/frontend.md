# 前端治理

> **适用角色**：designer（设计期）· coder（实现期）· reviewer（审查期）· supervisor（验收引用）。
> **定位**：管「前端代码要满足什么」，与 SKILL.md 的治理面（谁在什么阶段交什么产物）互补。
> **项目特化**（技术栈、目录、组件库、UI spec 位置）不在本文件内置，落项目 `references/constitution.md`。

---

## F-1 归属优先于行数

**判据**：状态、动作、展示**各有归属**；治理目标**不是**文件行数变短。

| 归属 | 承担什么 |
|---|---|
| 页面 | 编排：组合区块、决定数据来源 |
| hook | 相关状态与动作（取数、提交、错误态） |
| 区块组件 | 对应展示区块 |
| 公共 UI | 基础行为（确认、表单、浮层） |

**反例（不算治理）**：把整页逻辑搬进一个巨型 hook；把全部状态透传给子组件 —— 复杂度没减少，只是换了地方。

---

## F-2 保存类动作的三态基线

必须同时区分三者：**服务端基线** / **已提交内容** / **当前草稿**。

- 响应成功 = **提交出去的那份内容**被服务端确认，**不等于**当前草稿已保存；
- 响应返回时**不得覆盖**响应之后用户输入的内容；
- 不得把「响应后的新输入」标记为已保存。

**可核探针**：提交 A → 响应返回前改成 B → A 的响应成功 ⇒ 断言界面仍显示 B，且保存状态为「未保存」。

---

## F-3 并发与重复提交

- 提交中必须有**可判定的忙碌态**（禁用 / loading），不能只靠按钮文案；
- 同一动作重复触发要有防护（幂等键或提交中去抖）；
- 忙碌态下的关闭 / 取消 / 重试语义必须写清（能关吗？关了提交怎么办？）。

---

## F-4 后台刷新不得覆盖未保存输入

自动刷新（轮询 / 推送 / 窗口聚焦刷新）遇到未保存草稿时：

- 保留草稿并标记冲突，或显式提示用户选择；
- **禁止**静默覆盖未保存输入。

---

## F-5 弹窗与浮层的行为约定（不只是样式）

每个弹窗/浮层必须约定六项，缺项视为该组件未完成：

1. 打开时焦点落点；
2. 关闭后焦点归还到哪；
3. 嵌套层级与关闭顺序；
4. 忙碌（提交中）能否关闭；
5. 遮罩点击 / Esc 是否可关；
6. 关闭语义 = 取消还是提交。

**判定**：把「统一颜色 / 统一圆角」当完成 = 未完成。

---

## F-6 复用既有能力

- 新页面 / 新浮层先核对项目已有的**确认类、表单类、浮层类**公共组件；
- 产物里必须点名：复用了哪个、哪些行为保持一致、哪些**有意不同**及原因；
- **禁**写「注意复用组件」这类无对象口号 —— 约定必须指到具体能力与具体位置。

---

## F-7 两本记录分工

| 内容 | 落在哪 |
|---|---|
| 工程规则（约定项 / 禁止项） | 项目约定文件（`constitution.md` / 项目 AGENTS） |
| 视觉与组件选型 | UI spec |

两者**不混写**：规则文件管「必须怎样」，UI spec 管「长什么样、用哪个组件」。
