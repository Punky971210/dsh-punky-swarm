## S-1 机械规则清单（MC-1..MC-8 提炼）

机械规则 = **不需要判断力**的结构检查：先跑脚本、后谈语义。八条的「校验什么」与「本团队落点」：

| 规则 | 校验什么（一句话） | 判定对象 | 本团队落点 |
|---|---|---|---|
| `MC-1` | 结构必需项在场、必需字段齐全、单值字段形态正确 | 文档根 ＋ 六类核心段及其字段 | 任务包必备段落齐（角色/目标/关键契约/`## 验收标准`/`## 约束`/产物契约/输出格式/预算行） |
| `MC-2` | 同类标识符在命名空间内唯一 | 契约、分支、模块、子系统、组装根 id | 同包 `AC-` 编号不重复；跨包引用带批次短码 |
| `MC-3` | 每个引用解析到**已声明** id 或已声明签名 | 归属、链步、来源事件、代码/测试追踪、架构引用 | spec 点名的模板 / 角色文件 / 能力须解析到**实存路径** |
| `MC-4` | UI 树结构有效（根种类、重复语义、元素引用） | UI 布局树节点 | 边界条款：仅含 UI 布局树的任务适用，见 S-5 |
| `MC-5` | 依赖无自依赖、无环 | 模块与子系统依赖表 | 任务包依赖以引擎 `lanes[].deps` 为真源；规格侧 DAG 不得与之冲突 |
| `MC-6` | 追溯与影响记账完整 | 活动契约 × 代码/测试追踪 ＋ 受影响文件清单 | 每条验收标准必须能指到**一个产物字段或一条命令** |
| `MC-7` | 集成记账一一对应 | 链步引用 × API 依赖表条目 | spec 声明的复用面须登记为交接口或依赖声明 |
| `MC-8` | 架构边界结构自洽（owned / exported / dependencies 三角） | 子系统定义 | 分层与依赖方向由 `backend.md` B-4 承载；含子系统划分时适用 |

**提炼中发现的一处差集**（源文档与源校验器不一致，写进本细则以免误读）：源文档只列 8 条，源校验器实际发 **9 个** `check_id` —— 多出**未文档化**的 `MC-0`（文件不可读 / 根非映射 / YAML 解析失败）。

## S-2 结构失败先于语义评审

机械规则未过 ⇒ **不进语义评审**。这不是偏好，是成本：结构缺项时做语义判断只会产出不可执行的结论。

- **禁**「先看语义、结构后补」；**禁**把结构缺项降级成 SHOULD / FYI。
- **可核形态**：报告里结构失败与语义结论**分段**；结构段非空时，语义段写「未进入」。
- **本团队落点**：`designer` 出包先自过结构（段落齐、编号唯一、引用可解析）；`reviewer` 收到结构缺项的包直接判 MUST 退回，不列优点。

## S-3 编号唯一与引用可解析

两条是同一件事的两面：编号是**指向**，唯一才有指向力；引用**解析得到**才算指向成立。

- **编号唯一**：同一命名空间内不重复 —— 重复即两条契约被读成一条。
- **引用可解析**：引用只能指向**已声明**对象；指向未声明对象 = **断链**，不是「待定」。
- **可核命令**（判据落地形态，两条都可直接抄）：
  - 重复检测：`grep -oE '<前缀>-[0-9]+' <产物> | sort | uniq -d` ⇒ **输出为空**
  - 悬空引用：被引 id 逐个 `grep -c` 到声明段 ⇒ **每项 ≥ 1**
- **本团队落点**：`coder` 的「## 实现说明」每处改动带的条目号，必须是任务包里**真实存在**的 `AC-` 编号；引用不存在的条目 = 实现说明不完整。

## S-4 追溯记账与依赖 DAG

- **每条活动契约必须有去处**：至少落在代码追踪或测试追踪**之一**（源侧要求「至少一条」，不是「都要有」）。
- **影响面清单三要件**：存在、非空、路径跨两份清单**唯一**；每个模块的实现文件恰在「改动」或「新建」之一。
- **依赖成 DAG**：无自依赖、无环；跨边界依赖须**两侧同时允许**（调用方列出该依赖 ＋ 被调方声明导出）。
- **本团队落点**：
  - 任务包每条验收标准必须给**命令或可核读数** —— 无去处的不叫验收标准，叫愿望；
  - 任务包之间的依赖**以引擎 `lanes[].deps` 为唯一真源**；规格里画的 DAG 与之不一致时，以引擎为准并改规格（防第二本账）；
  - 跨层依赖方向按 `backend.md` B-4 单向。

## S-5 UI 树结构有效性（边界条款）

**适用条件**：仅当产物**含 UI 布局树**时启用。本团队常规任务不含该形态（交互面由 `frontend.md` F-1..F-7 承载）。

- 屏幕根只能用**整屏容器种类**（页面 / 屏幕 / 模态 / 抽屉 / 面板 / 全屏浮层），不得用普通容器充当屏幕根；
- 重复标记**只能**挂在声明了元素 id 的节点上，取值收敛为三种重复语义；
- 同一元素 id 在树里出现多次，**只允许**其每次出现都标「任意重复」语义；
- 伪代码引用的元素必须解析到已声明元素 id。
- **本团队处置**：本团队**不引入**源仓的 UI 组件种类注册表 ⇒ 本条只作**边界记录**，**不新增检查、不新增门禁**；将来引入 UI 树形态时，须先给**可达负例**再落判据。
- 锚点：`speclang-waterfall/assets/MECHANICAL_RULES.md:57`

## S-6 六态证据语法

四档强度 ＋ 两个旁路态。**六态是结论词汇表，不是形容词** —— 每条结论必须落到一个态上。

| 态 | 类别 | 计入通过 | 触发条件 |
|---|---|---|---|
| `PROVED` | 强度档 | 是 | 未发现反例，且证据链**闭合**（每步有行号与规则支撑，收束成立） |
| `SEMI_PROVED` | 强度档 | 是（附条件，见 S-7） | 未发现反例、主体成立，但仍依赖未闭合假设 / 外部语义前提 / 待补证环节 |
| `VIOLATED` | 强度档 | 否（且必入修复清单） | 找到最小反例路径并能回指证据 |
| `UNKNOWN` | 强度档 | **否** | 未找到反例，但证据链**不闭合** |
| `CHAIN_BREAK` | 旁路（链级） | 否（且必入修复清单） | 链上相邻两步断言不蕴含：上游给出的不满足下游需要的 |
| `MAPPING_BLOCKED` | 旁路（映射级） | 否（且必入修复清单） | 无法用代码证据建立入口 / 调用链 / 状态映射 ⇒ 该契约**全部义务统一判 `UNKNOWN`** |

- **`CHAIN_BREAK` 必带四件**：断裂点（哪两步之间）、上游给定、下游需要、不蕴含原因（一行 ＋ 行号）。缺任一 ⇒ 该结论不成立。
- **`MAPPING_BLOCKED` 的连带规则**是最容易误用处：它不是「这条先跳过」，而是**该契约整族义务降为 `UNKNOWN`** —— 不得对其中几条另给 `PROVED`。
- 锚点：`speclang-hoare-check/assets/hoare-reasoning-report-template.md:4,45,83,92`；`speclang-hoare-check/SKILL.md:49`

## S-7 记分口径与修复清单位置

- **`UNKNOWN` 不计通过**：计数里不进分子。理由：证据链不闭合的结论与「没做」等价。
- **`SEMI_PROVED` 可计通过，但必须补证**：风险说明须给三件 —— **原因**、**风险范围**、**补证计划**。三件齐备才计入通过；缺项时**本团队口径**按 `UNKNOWN` 计。
  - **口径来源须标注**：源侧只要求「解释原因、范围与补证计划」，**未规定**缺项后果 —— 缺项降级是本团队加严，不得写成源侧规定。
- **必入修复清单四态**：`UNKNOWN`、`VIOLATED`、`MAPPING_BLOCKED`、`CHAIN_BREAK` —— 四者**任一**不出现在修复清单 = 报告不完整。
- **概要行分族计数**：按「API 类 / 用例类」两族**分别**给六态计数，不合并成一个总数（合并会掩盖「API 全证、用例全挂」）。
- **本团队落点**：`tester` / `reviewer` / `supervisor` 的产物给该计数；`supervisor` 的验收结论**不得**把 `UNKNOWN` 计入通过项。

## S-8 报告机读行与退出码

- **逐条块形态**（五字段，固定顺序；字段名是**协议词**，不得改写）：

| 字段 | 取值 | 要求 |
|---|---|---|
| `CHECK` | `[<规则族>-<n>]: <检查名>` | 一条检查一行 |
| `STATUS` | `PASS` / `FAIL` / `WARN` | 三值互斥 |
| `FINDING` | 具体发现 | 不写「有问题」类空话 |
| `LOCATION` | `<段.字段>` 或 `<文件:行>` | 精确到可定位 |
| `ACTION REQUIRED` | 交付前须修什么 | 可执行，不写「建议优化」 |

- **汇总行**：**独立一行**，以 `SUMMARY:` 起，两个计数（失败数、警告数）＋ 方括号内**单一**门控词 —— 失败数 > 0 用 `BLOCK`，否则用 `PROCEED`；**二者互斥，不得并列**。
- **排序纪律**：先列全部失败，再列警告；同族按规则 id 分组。
- **退出码口径**：失败数 > 0 ⇒ `1`；失败数 = 0 ⇒ `0`。**警告多少不影响退出码**（警告是记账，不是阻断）。
- **硬失败边界**：机械或合规类失败属**交付前硬失败**，在解决前不得进入语义评审、不得交下游交接。
- **本团队落点**：`tester` 的测试报告与 `reviewer` 的审查报告尾部给该行；该行可直接作任务包 `gate: <命令>` 的阻断判据（与 `verification.md` V-2「失败是否真的阻断」联动）。
- 锚点：`speclang-waterfall/assets/reporting_requirements.md:6-10,16,19`；`speclang-waterfall/assets/validate_speclang_mechanical.rb:1086,1090`

## S-9 需求编号纪律

编号是**稳定指针**：一经分配不复用、不重编号、不借位。五族用途：

| 族 | 用途 | 形态 |
|---|---|---|
| `REQ-nnn` | 需求点唯一编号（每个重要需求必有） | `REQ-001` |
| `SCN-nnn` / `SCN-nnn-B<k>` | 场景 / 该场景的分支场景（分支**挂父编号**） | `SCN-001` / `SCN-001-B1` |
| `RULE-nnn` | 跨场景复用的规则（不依附单一操作） | `RULE-001` |
| `IDX-nnn` | 分类索引：给既有需求 / 场景打**轻量标签**，不重写正文 | `IDX-001` |
| `AC-nnn` | 验收检查点（覆盖对象 ＋ 检查重点 ＋ 通过标准） | `AC-001` |

- **引用纪律**：只能按编号引用，**禁**「上文那条」「前面提到的」类相对指代。
- **覆盖判据**（源侧就绪检查中属机械面的 5 项提炼）：① 每个重要需求都有编号；② 每个需求都被场景 / 规则 / 界面理解 / 验收检查点 / 范围外**之一**覆盖；③ 用户能感知到的异常与特例，每条都要有对应的场景分支；④ 分类索引用轻量标签区分流程 / 界面反馈 / 数据状态 / 外部影响；⑤ 验收检查点能追到需求点与场景。
- **本团队落点**：任务包 `## 验收标准` 的 id 列用该族形态（本团队既有惯例 `AC-n`，与 `REQ-` 族并存不冲突）；**跨族不得互相顶替** —— `AC-` 不能当需求编号用，`REQ-` 不能当验收标准 id 用。
- 锚点：`prd-guide/assets/prd-template.md:20,42-43,61,69,102,124-125`

## S-10 需求点 → 契约 这一跳：当前无人机械核

**事实（不掩饰）**：S-4 的记账规则只核「每个**契约**至少有去处」，**不核**「每条**需求点**是否被某条契约承接」。源侧把这一跳放在人工 / AI 判断的工作流输出里（需求覆盖清单），**明确不属于机械面**。

本团队现状与缺口：

1. 任务包的 `AC-nnn` 与（若有）`REQ-nnn` 之间**没有机检门**：既无脚本比对「spec 出现的需求集 ⊆ 验收段覆盖集」，也无反向。
2. ⇒ 需求漏接（写了需求、没写验收）与幽灵验收（验收追不到需求）**都能静默通过**。
3. 处置（本文件**只登记缺口，不新造门禁**）：
   - **眼下**：由 `reviewer` 人工核对，结论标 `SEMI_PROVED` 并写明「人工核，非机器已证」；
   - **将来机器化**：最小可行判据 =「spec 内需求编号集 ⊆ 验收段覆盖集」，且**先给可达负例**（构造一条漏接需求应判红）—— 改前就已绿的判据即假绿，不得采用。
- 锚点：`speclang-waterfall/assets/MECHANICAL_RULES.md:85`（记账规则的范围边界）；`speclang-waterfall/assets/reporting_requirements.md:23-29`（覆盖清单属工作流输出，非校验器）
