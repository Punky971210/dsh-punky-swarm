# 后端治理

> **适用角色**：designer（能力归属与契约）· coder（实现）· reviewer（审查）· coordinator（摸底时标唯一归属）。
> **定位**：管「后端能力该归属谁、边界在哪」，与 SKILL.md 治理面互补。
> **项目特化**（分层目录名、错误码表、鉴权中间件）落项目 `references/constitution.md`。

---

## B-1 入口可多，能力必须单一

入口（HTTP API / 智能体工具 / workflow 节点 / 定时任务 / CLI）可以不同；**核心能力必须复用同一实现**。

- **禁止**：在某个入口里重新实现一遍推理、导出、写库、解析；
- **可核判据**：同一能力在调用链矩阵（`references/templates/call-chain-matrix-template.md`）里只有**一个终结点**（一个 service 方法）；
- **正例**：新入口 → 参数校验 → 调既有 service。

---

## B-2 权限与数据边界不因入口而放宽

- API 做了鉴权 **≠** 工具 / workflow / 定时任务可以绕过；
- 所有入口遵守**同一套**权限与数据边界；
- **可核判据**：权限校验位于**能力层或统一中间件**，不由各入口各自实现一遍（各自实现 = 必然出现口径分叉）。

---

## B-3 共享能力必须有唯一归属

- 每项能力（如图片入库、结果解析、导出）标注**唯一归属模块**；
- 要统一的是「**同一项能力**」，**不是**把所有相似代码塞进一个越来越大的巨型类；
- **可核判据**（二选一，按当前可用工具取）：① 用**代码图谱类 MCP** 检索该能力的实现点 = 1（或 1 主实现 + 显式适配层）；② 无图谱可用时，用全仓调用点检索给出「实现点清单」并逐条说明。超过 1 处均需在产物里说明为何必须分叉。

---

## B-4 分层与依赖方向

```
API 层（鉴权 / 参数校验 / 响应映射）
   ↓ 单向
业务 service（业务规则 / 编排）
   ↓ 单向
执行器 / 仓储（真实运行、数据读写、外部调用）
```

- 依赖**单向**，禁止反向 import（下层不得引用上层）；
- **可核判据**：给出一条具体路径断言，如「`<api 目录>/` 内零跨层 import」（路径按项目填）。

---

## B-5 异常体系

| 要素 | 要求 |
|---|---|
| 预期业务失败 | 稳定**错误码** + 对调用方**安全的 message** + **结构化详情** |
| HTTP 边界 | 负责把错误码**映射**为状态码 |
| 未知异常 | 内部细节（堆栈、SQL、内网地址）**只进服务端日志**，不回给调用方 |

- **可核判据**：同一错误码在端点契约（`references/templates/endpoint-behavior-template.md`）里语义**唯一**；调用方**不依赖**异常类名或 message 文案做分支。

---

## B-6 迁移 ≠ 移文件

移动 / 改目录后必须逐项核对：

1. 旧接口是否还在（是否已下线、是否仍被调用）；
2. 错误结构是否变化（错误码 / 详情形状）；
3. 导入路径是否断裂；
4. 调用方是否被破坏；
5. 发布目录能否正常导入。

**真正要收敛的三样**：能力归属、依赖方向、调用契约。移动文件**不等于**完成重构。
