## 1. 模板正文（plan lane 直接照此产出）

````markdown
# 规格说明：[功能名称]

## 概述
一句话：这个功能是什么？

## 问题
为什么需要它？
- 现状：用户今天怎么做
- 痛点：具体的问题
- 影响面：这个问题有多大？

## 方案
高层：我们要建设什么？
- 核心思路：主要概念
- 非目标：我们**不做**什么

## 需求
### 功能需求
- [ ] 用户可以通过 [方式] 完成 [动作]
- [ ] 系统将 [数据] 存储于 [位置]
- [ ] [场景 A] 产生 [结果]

## 约束
- 性能：P95 < 200ms
- 可用性：99.9% 可用率
- 安全：符合 OWASP Top 10
- 可扩展性：10 倍增长无需改造
- 关键依赖与版本约束见下表

| 依赖 | 用途 | 版本约束 |
|------|------|---------|
| [依赖名称] | [用途描述] | [版本范围] |

## 接口设计
[如适用，给出请求/响应结构]

### POST /api/v1/users/register
请求：
```json
{"email": "user@example.com", "password": "..."}
```
响应：
```json
{"data": {"id": "uuid", "email": "..."}}
```

## 接口契约引用
[端点 → 参考文档路径]

| 端点 | 方法 | 参考文件路径 |
|------|------|-------------|
| /api/v1/[资源] | GET/POST/PUT/DELETE | contracts/[文件].md |

## 验收标准
- [ ] 用户可以用合法邮箱 + 密码注册
- [ ] 邮箱重复返回 409
- [ ] 邮箱非法返回 422
- [ ] 密码经哈希存储（不得明文）
- [ ] 自动发送验证邮件

## 测试策略
- 单元测试：[清单]
- 集成测试：[清单]
- 端到端测试：[清单]

## 成功指标
如何判断这件事值得做？
- [ ] [指标 1]
- [ ] [指标 2]

## 时间线
- 设计评审：[日期]
- 实现：[N] 天
- 测试：[N] 天
- 上线：[日期]

## 待决问题
- [问题 1]：[谁来回答]
- [问题 2]：[谁来回答]

## 质量自查
- [ ] 问题表述清晰（不含糊）
- [ ] 方案与问题匹配
- [ ] **全部验收标准可测**
- [ ] 无模糊措辞（「应该」「可能」「也许」）
- [ ] 时间线现实
- [ ] 新人可照此规格实现
- [ ] 评审完成（设计 / 工程 / 产品）
````

## 2. 英中对照（供宿主侧 `SKILL.md` 同步修改）

| 原文章节 | 中文章节 | 是否引擎判据章 |
|---|---|---|
| `# Specification: [Feature Name]` | `# 规格说明：[功能名称]` | — |
| `## Overview` | `## 概述` | — |
| `## Problem` | `## 问题` | — |
| `## Solution` | `## 方案` | — |
| `## Requirements` / `### Functional` | `## 需求` / `### 功能需求` | — |
| `### Non-Functional` | **归入 `## 约束`**（另加「关键依赖」表） | ★ **是** |
| `## API Design` | `## 接口设计` | — |
| `## Key Dependencies` | **归入 `## 约束`**（表格保留） | — |
| `## API Contracts 引用` | `## 接口契约引用` | — |
| `## Acceptance Criteria` | `## 验收标准` | ★ **是** |
| `## Testing Strategy` | `## 测试策略` | — |
| `## Success Metrics` | `## 成功指标` | — |
| `## Timeline` | `## 时间线` | — |
| `## Open Questions` | `## 待决问题` | — |
| （原文 `## Spec Quality Checklist`） | `## 质量自查` | — |

**两处结构归并的说明**（这是本地化唯一的实质改动，非「翻译」）：

1. `### Non-Functional`（性能/可用性/安全/可扩展）与 `## Key Dependencies` 在语义上都是**约束**，
   故归并为一章 `## 约束` —— 它同时是引擎判据章之一。⇒ **信息量不减**（原表格逐字保留）。
2. 原「Spec Quality Checklist」与「Quality checks」是**同一份清单的两种写法**，
   合并为末尾 `## 质量自查`（去重后 7 条）。

## 3. 判据与配置（引擎侧）

**引擎默认判据（全中文，单一真源 `lib/assembly/flows.js#ENGINE_BASELINE_CRITERIA_SECTION`）**：

| 判据门 | 位置 | 默认章节 | 说明 |
|---|---|---|---|
| **锚点门** `GATE_AUDIT_CRITERIA_MISSING` | `lib/state/gates.ts`（audit lane 派发前） | `## 验收标准` | audit 的 `consume` 中 plan 产物须带该章 |
| **契约门** `GATE_PLAN_CONTRACT` | 同上（plan lane 结算前） | `## 验收标准` + `## 约束` | 无 `contract` 声明时按两章校验 |

**配置化通道**（声明面优先，缺声明回落引擎基线）：

| 面 | 键 | 取值 | 归属 |
|---|---|---|---|
| plan 层内容契约 | `flows.plan.contract.required_sections` | 非空字符串数组 | 团队资产（既有键） |
| audit 层职责声明 | `flows.audit.audit_contract.criteria_section` | 非空字符串（**本轮新增**） | 团队资产（新增键） |

⇒ **规格与判据由此解耦**：若某团队坚持用英文章节名，只需在资产里声明
`criteria_section: "## Acceptance Criteria"` / `required_sections: ["## Acceptance Criteria", "## Constraints"]`，
**代码零改动**。默认（不声明）则为全中文。
